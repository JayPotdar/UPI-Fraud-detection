# UPI Transaction Fraud Detection & Risk Scoring System

An end-to-end machine learning project for detecting potentially fraudulent UPI transactions using transaction-level behavioral features, class-imbalance techniques, model evaluation, explainability, and a FastAPI-based inference API.

> **Note:** This project is intended as a machine learning and fraud analytics case study. The final model has limited fraud discrimination because of the available dataset and should not be considered production-ready.

---

## 1. Project Overview

UPI fraud detection is a highly imbalanced classification problem because fraudulent transactions represent only a very small fraction of total transactions.

This project builds an end-to-end fraud detection workflow covering:

- Exploratory Data Analysis (EDA)
- Data preprocessing
- Feature engineering
- Class imbalance handling
- Logistic Regression
- Random Forest
- XGBoost
- SMOTE experiments
- Hyperparameter tuning
- Threshold analysis
- Model explainability using SHAP
- Model serialization using Joblib
- REST API development using FastAPI

The final system accepts transaction information through an API and returns a fraud-risk score and classification.

---

## 2. Dataset

The dataset contains approximately **250,000 UPI transactions**.

Fraud is extremely rare:

- Genuine transactions: approximately **99.8%**
- Fraudulent transactions: approximately **0.2%**

Because of this imbalance, accuracy alone is not an appropriate evaluation metric.

The project focuses primarily on:

- Recall
- Precision
- F1-score
- Confusion Matrix
- ROC-AUC
- PR-AUC

---

## 3. Features

The final model uses 18 input features.

### Transaction Features

- Transaction type
- Merchant category
- Transaction amount
- Transaction hour
- Day of week

### Customer / Account Features

- Sender age group
- Receiver age group
- Sender state
- Sender bank
- Receiver bank

### Device / Network Features

- Device type
- Network type

### Engineered Features

The following features were derived from the original transaction information:

- `is_weekend`
- `night_transaction`
- `same_bank`
- `same_age_group`
- `high_value_transaction`
- `peak_hour`

These engineered features are automatically generated by the API before the transaction is passed to the model.

---

## 4. Data Leakage Prevention

Potential leakage variables were excluded from model training.

For example, features representing information that would only become available after the transaction outcome were avoided.

This ensures that the model only uses information that could realistically be available when a transaction is being evaluated.

---

## 5. Data Preprocessing

Categorical variables were transformed using:

```text
OneHotEncoder
```

Numerical variables were standardized using:

```text
StandardScaler
```

Binary engineered features were passed directly to the model.

The final preprocessing pipeline transforms the **18 input features into 62 model features**.

The preprocessor is fitted only on the training data to prevent data leakage.

---

## 6. Train/Test Split

The dataset was split using stratified sampling:

```python
train_test_split(
    X,
    y,
    test_size=0.20,
    random_state=42,
    stratify=y
)
```

Stratification ensures that the very small fraud proportion is represented in both training and test sets.

---

## 7. Handling Class Imbalance

Several approaches were investigated.

### Class Weighting

Logistic Regression was trained using:

```python
LogisticRegression(
    class_weight="balanced",
    random_state=42
)
```

This increases the importance of the minority fraud class during training.

### SMOTE

SMOTE was tested by oversampling the minority fraud class in the training data.

Models trained after SMOTE included:

- Logistic Regression
- Random Forest
- XGBoost

SMOTE did not produce a meaningful improvement in fraud discrimination for this dataset.

### XGBoost Class Weighting

`scale_pos_weight` was also investigated as an imbalance-handling technique for XGBoost.

---

## 8. Models Evaluated

Multiple classification approaches were evaluated:

| Model | Imbalance Strategy |
|---|---|
| Logistic Regression | Class Weighting |
| Random Forest | Class Weighting / SMOTE experiments |
| XGBoost | `scale_pos_weight` / SMOTE experiments |
| Logistic Regression | SMOTE |

The experiments showed that more complex models did not provide a meaningful improvement over the Logistic Regression baseline.

Therefore, Logistic Regression with class weighting was retained as the final model because it provides a simple and interpretable baseline.

---

## 9. Final Model

The final model is:

```text
Logistic Regression
+
class_weight="balanced"
```

The final model does **not** use SMOTE during inference.

The production model uses the original 18-feature configuration rather than later experimental log-transformed and cyclical features.

---

## 10. Threshold Analysis

Fraud detection involves a trade-off between:

- detecting more fraud transactions, and
- generating false-positive alerts.

Multiple classification thresholds were evaluated.

The deployed operating threshold is:

```text
0.50
```

This threshold was selected to prioritize fraud recall over reducing false positives.

However, the model still produces a substantial number of false positives, demonstrating that threshold tuning alone cannot compensate for weak predictive signal in the available features.

---

## 11. Model Explainability

The model was analyzed using both Logistic Regression coefficients and SHAP.

Explainability techniques included:

- Logistic Regression coefficient analysis
- SHAP global feature importance
- SHAP beeswarm plots
- SHAP local waterfall explanations

A local SHAP analysis demonstrated how multiple transaction characteristics could push a genuine transaction toward a high fraud-risk score.

This helped identify why the model generates false-positive predictions.

---

## 12. Key Finding

One of the main conclusions of this project is:

> **Handling class imbalance alone is not sufficient to build an effective fraud detection system.**

Class weighting, SMOTE, Random Forest, XGBoost, hyperparameter tuning, and threshold tuning were investigated.

Despite these experiments, fraud and genuine transactions remained difficult to separate reliably.

This suggests that the main limitation is the predictive information available in the dataset rather than simply the choice of classification algorithm.

---

## 13. Potential Improvements

A real-world fraud detection system would benefit from richer behavioral and historical information such as:

- Transaction velocity
- Number of recent transactions
- Customer spending deviation
- Historical average transaction amount
- New-device detection
- Device change frequency
- Beneficiary history
- New-beneficiary detection
- Account age
- Merchant risk history
- Customer fraud history
- Geographic anomalies
- Distance from usual transaction locations

These features could provide stronger signals for distinguishing genuine behavior from fraud.

## 15. FastAPI Inference API

The trained model is exposed through a REST API built using FastAPI.

The API accepts raw transaction information.

It then:

```text
Transaction JSON
        ↓
Pydantic Input Validation
        ↓
Feature Engineering
        ↓
Saved Preprocessor
        ↓
62 Transformed Features
        ↓
Logistic Regression
        ↓
Fraud Risk Score
        ↓
Decision Threshold
        ↓
Fraud / Genuine
```

### Start the API

Activate the virtual environment and run:

```bash
uvicorn app:app --reload
```

The API will run locally at:

```text
http://127.0.0.1:8000
```

Interactive Swagger documentation is available at:

```text
http://127.0.0.1:8000/docs
```

## 19. Limitations

The final model should **not be considered production-ready**.

The dataset contains very few fraud examples, and the available transaction-level features provide limited separation between genuine and fraudulent transactions.

The project therefore focuses not only on obtaining predictions, but also on demonstrating:

- correct evaluation of imbalanced classification
- experimentation with imbalance-handling techniques
- prevention of data leakage
- model explainability
- threshold analysis
- reproducible model inference
- API-based model serving

---

## 20. Conclusion

This project demonstrates an end-to-end machine learning workflow for UPI fraud detection, from exploratory analysis and feature engineering through model experimentation, explainability, serialization, and API deployment.

A key learning from the project is that improving a fraud detection system requires more than selecting increasingly complex algorithms. When the underlying features contain limited predictive signal, techniques such as class weighting, SMOTE, hyperparameter tuning, and threshold optimization cannot by themselves produce a reliable fraud detector.

The next stage toward a stronger system would be incorporating historical and behavioral transaction features that better represent abnormal customer activity.
